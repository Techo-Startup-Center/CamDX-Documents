# CamDX 7.8.2 Release Notes

## Status: DRAFT

This document explains what "CamDX 7.8.2" actually means at this stage — what has been validated, what has been adapted, and what remains open. It does **not** constitute an announcement of whole-estate production migration, and it is **not** an authorization for members to begin upgrading.

## 1. Upstream basis

X-Road 7.8.2.

## 2. Validated CamDX packages

| Track | Package version | Status |
|---|---|---|
| Ubuntu 22.04 Jammy | `7.8.2-1.ubuntu22.04` | Validated |
| Ubuntu 24.04 Noble | `7.8.2-1.ubuntu24.04` | Validated |
| RHEL 9 | `7.8.2-2.el9` | Validated (following a defect-fix cycle from an initial `-1.el9` build) |

All three tracks were built from the CamDX source `master` branch merge `2b0ac35b64b45b4e433605ed2c9d890cfdf5ea2a` (PR #16). The `7.8.2` Git tag remains on its existing commit and was not moved as part of this validation work.

## 3. Completed validation scope

Describing only what has been evidenced complete:

- Release-mode source compile, verified against a clean JDK21 build container.
- Debian packaging for both Jammy and Noble tracks (28 packages each), including CamDX PKI class verification, branding verification, and confirmation of no development/`SNAPSHOT` residue.
- A Jammy production canary deployment (operator-executed, GO).
- RPM packaging for RHEL 9 (19 packages), including a defect-fix cycle addressing a PostgreSQL fresh-install readiness race condition and a systematic RPM file-permission normalization defect, verified via a static permission-audit tool built for this purpose.
- A signed RHEL 9 production canary deployment, including a host reboot, and promotion through canary and public release repository stages with a 19/19 package round-trip verification at each stage.
- A containerized Security Server Sidecar candidate: build/provenance validation, controlled runtime validation (initialization, PKI, registration, live API exchange, local and remote Operational Monitoring), container restart persistence, mandatory destroy/recreate persistence, full host-reboot recovery, a deployment-definition (`.env`) credential-corruption finding and controlled repair (proven durable under an unattended Compose recreate), and an operations/logging readiness review.
- Public container publication: `ghcr.io/techo-startup-center/camdx/security-server:7.8.2` and `:noble-7.8.2`, both independently verified as publicly, anonymously pullable and resolving to the identical immutable digest `sha256:95fa519adf660cf6e61a037ba9250dfdb1467ec06d6a292dbfccc09db7d71c0b`, which itself resolves to the same frozen `linux/amd64` Image ID validated in the bullet above. No `latest` tag was published. The GHCR package is linked to its source repository, `Techo-Startup-Center/CamDX` (public).

## 4. CamDX adaptations (where evidenced)

- CamDX branding present and verified across all package tracks and the container candidate.
- Cambodia/CamDX PKI adaptations (CamDX-specific PKI classes) present and verified, with member-specific certificate/test data sanitized out of the shipped packages.
- CamDX package naming conventions restored/aligned (e.g. `camdx-*` package names, version strings matching the tracks in §2).
- Separate, explicitly distinct Jammy and Noble Ubuntu package tracks (not a single ambiguous "Ubuntu" track), and a separate RHEL 9 track.

## 5. Separate / open tracks

The following remain explicitly **open** and are **not** closed by the package validation described above:

- **High Availability validation** — standalone package validation does not automatically validate the HA procedures. See [`../security-server/ubuntu/high-availability-installation.md`](../security-server/ubuntu/high-availability-installation.md) and [`../security-server/rhel/high-availability-installation.md`](../security-server/rhel/high-availability-installation.md), both currently status **REQUIRES VERIFICATION**.
- **Member Migration & Release Readiness** — has not started; behind an explicit authorization gate. **The member migration implementation pattern (Parallel Replacement / Blue-Green) is approved** (decision `03-A2`), and a corresponding operator procedure draft exists ([`../security-server/upgrade/parallel-replacement.md`](../security-server/upgrade/parallel-replacement.md)) — this is not the same as the Member Migration & Release Readiness track itself starting, and does not authorize any member's production migration. See [`../security-server/upgrade/README.md`](../security-server/upgrade/README.md).
- **Central Server 7.8.2 validation** — a separate, currently active engineering track (development Central Server DR-clone upgrade and validation), not covered by this release note and not completed by anything described above.
- **Production Central Server migration** — not authorized by anything in this release note.
- **MV-GC-01 HTTPS compatibility validation** — remains open.
- **CamDX Meter / Operational Monitoring end-to-end ingestion validation** — remains open; local and remote Operational Monitoring *mechanism* health was validated as part of the container candidate's runtime testing, but end-to-end CamDX Meter ingestion is a separate, not-yet-validated track.
- **Overall CamDX 7.8.2 production rollout** — not closed. Package and container publication being complete does not, by itself, mean the platform is ready for production-wide use — every item in this section must close first.

Container publication itself (GHCR) is **complete** as of this release note (see §3) — it is listed here only to make clear that publication completing does **not** also close any of the other tracks above.

## 6. What this release note does not claim

This document does not present the completed package validation described in §3 as approval for whole-estate production migration, as a substitute for the open tracks in §5, or as authorization for any member to begin an in-place upgrade — see [`../security-server/upgrade/README.md`](../security-server/upgrade/README.md) for why an in-place upgrade based on the fresh-installation guides is explicitly unsupported.
