# CamDX Security Server — Deployment Model Selector

## Status / scope

**Status: SAFE/EVIDENCED for the comparative framing and current CamDX validation status of each model; individual model detail defers to that model's own guide.** This document does not introduce any new procedure — it exists to help a new or existing CamDX member choose among the deployment models CamDX already documents elsewhere, using precise, current policy language. It does not authorize a migration between models for an existing member; see [`upgrade/README.md`](./upgrade/README.md) and [`upgrade/parallel-replacement.md`](./upgrade/parallel-replacement.md) for that separately-gated topic.

This document does not duplicate installation steps. For each model it links to the guide that owns the actual procedure.

## 1. The principle that governs every model below

**Containerization reduces deployment and environment variability. It does not make the Security Server stateless.**

Whether a Security Server runs as native Ubuntu/RHEL packages or as the container Sidecar, it carries the same categories of state — but not every category has the same backup/restore requirement, and this document does not treat them as equivalent:

**A. Durable/persistent state — must be backed up, cannot be regenerated:**
- Member/subsystem identity and Security Server Code.
- AUTH/SIGN key material and certificates (software token or HSM-backed).
- `serverconf` (registration, client/service configuration).
- `messagelog` and Operational Monitoring data (legally/operationally significant transaction records — as applicable per deployment).

**B. Rebuildable/cache/runtime state — its own retention semantics, not a default backup candidate:**
- OCSP response cache — deliberately non-replicated even in the replicated HA architecture ([`ubuntu/high-availability-installation.md`](./ubuntu/high-availability-installation.md) §5, §10 — see Model E, §7 below); expected to regenerate from a live OCSP responder query rather than from a restored backup.
- Global-configuration cache — independently, continuously refreshed by each Security Server's own `confclient` process, not a value to restore from a stale backup.
- Other cache/archive classes (e.g. messagelog archive **files**, as distinct from the messagelog **database** — see [`container/production-hardening-checklist.md`](./container/production-hardening-checklist.md) item 14) carry their own, separately-determined retention model, not automatically inherited from category A's backup treatment.

Choosing a deployment model changes **how** category A's state is packaged, deployed, and operated — it does not remove the requirement to explicitly plan that state's backup, retention, recovery, and lifecycle management, and it does not change category B's state into something requiring the same treatment. A model that makes deployment easier is not automatically a model that makes state management easier; several models below (in particular the container standalone model, §5) currently have open backup/restore/upgrade-rehearsal items precisely because deployment ease has been validated before full state-lifecycle hardening has. See [`ubuntu/high-availability-installation.md`](./ubuntu/high-availability-installation.md) §10 for the same durable/per-node/rebuildable three-way distinction applied in full detail to the HA backup case.

## 2. Quick comparison

| Model | Intended use | CamDX 7.8.2 status | CamDX recommendation |
|---|---|---|---|
| A. Ubuntu native standalone | General-purpose new deployment | **APPROVED** | Recommended native option |
| B. RHEL native standalone | Institutional/security-policy-driven new deployment | **APPROVED** | Supported native option |
| C. Container standalone | Greenfield deployment with mature container operations | **APPROVED** | Preferred greenfield option where container operations are mature — not yet the universal default |
| D. Independent Security Servers (simple redundancy) | Redundancy without shared-state replication complexity | Preferred simple redundancy model candidate; **targeted CamDX validation required** | Preferred simple-redundancy candidate, pending targeted validation |
| E. Replicated external-load-balancer HA cluster | Existing members' established HA architecture | Supported existing architecture, upstream-aligned; **CamDX 7.8.2 validation required** | Continue supporting existing users; do not present as APPROVED for 7.8.2 yet |
| F. Container/Kubernetes HA | Cloud-native HA for container-operations-mature members | Upstream-supported; **CamDX validation required** | Not yet CamDX-approved HA; do not replace model E with this |

None of the redundancy/HA models (D, E, F) should be read as interchangeable with one another — they have materially different failure semantics, operational complexity, and evidence bases. See §5–§7.

## 3. Model A — Ubuntu native standalone

- **Intended use:** a strong, well-evidenced general-purpose choice for a new member with no specific RHEL requirement — **not** presented as the universal/default choice ahead of container standalone (Model C) where a member's own container operations are already mature; see §5.
- **Operational prerequisites:** a supported Ubuntu 22.04 (Jammy) or 24.04 (Noble) host; standard `apt`-based package operations; local or remote PostgreSQL per [`ubuntu/standalone-installation.md`](./ubuntu/standalone-installation.md).
- **Advantages:** broadest CamDX operational history; most extensively evidenced installation guide; native systemd service management; straightforward troubleshooting via [`troubleshooting/connectivity.md`](./troubleshooting/connectivity.md).
- **Trade-offs:** host-level OS patching/lifecycle is the member's own responsibility; no built-in redundancy (see §5–§7 for that).
- **CamDX 7.8.2 validation status:** **APPROVED.** Both Jammy (`7.8.2-1.ubuntu22.04`) and Noble (`7.8.2-1.ubuntu24.04`) tracks validated — see [`../release-notes/7.8.2.md`](../release-notes/7.8.2.md).
- **CamDX recommends this when:** the member has no specific RHEL/container mandate and wants the most-evidenced native path.
- **CamDX does not recommend this when:** institutional policy mandates RHEL, or the member's own operations are already container-native and mature (see Model C).

## 4. Model B — RHEL native standalone

- **Intended use:** members whose institutional infrastructure or security policy requires RHEL.
- **Operational prerequisites:** RHEL 9 host; SELinux Enforcing (validated baseline, not disabled); `dnf`-based package operations; EPEL for the confirmed dependency set. See [`rhel/standalone-installation.md`](./rhel/standalone-installation.md).
- **Advantages:** aligns with RHEL-centric institutional security/patching programs; SELinux Enforcing validated as the baseline (not a documentation gap requiring a disable step).
- **Trade-offs:** slightly smaller evidence base than Ubuntu (defect-fix cycle was required to reach the validated `7.8.2-2.el9` build); firewalld/SELinux-specific operational knowledge required.
- **CamDX 7.8.2 validation status:** **APPROVED** (`7.8.2-2.el9`).
- **CamDX recommends this when:** institutional policy prefers or mandates RHEL.
- **CamDX does not recommend this when:** the member has no RHEL requirement and would otherwise benefit from Ubuntu's larger evidence base, or is a container-native greenfield deployment (Model C).

## 5. Model C — Container standalone (Security Server Sidecar)

- **Intended use:** **preferred greenfield option specifically where the member's own operations are already container-native and mature** — not a universal replacement for native installation, and not a recommended migration target for an existing stable native Security Server merely because a container image exists.
- **Operational prerequisites:** a Docker host (`x86_64`/`linux/amd64`), Docker Engine + Compose v2, and — critically — an operational team already comfortable with container lifecycle management (image pinning, volume/persistence discipline, log retention, Docker-host hardening). See [`container/deployment.md`](./container/deployment.md) and the companion [`container/production-hardening-checklist.md`](./container/production-hardening-checklist.md).
- **Advantages:** single digest-pinned artifact removes host-package-drift variability; Operational Monitoring and the messagelog archiver are baked in and running by default (no separate install step, unlike native); fast, repeatable deployment.
- **Trade-offs:** the Security Server's state is exactly as persistent as in the native case, but its persistence mechanics differ **per state category**, not as a single "named volume + external database" generalization — see the approved [`container/deployment.md`](./container/deployment.md) evidence precisely:
  - `/etc/xroad` (identity, keys, configuration, `db.properties`) — persisted via its own named Docker volume (§10).
  - `serverconf`/`messagelog`/OPMON data — held in the validated **external `postgres:16` container's own separate named volume** (§8, §11), distinct from the `/etc/xroad` volume.
  - Message-log **archives** and OCSP/global-configuration **cache** have their own retention/regeneration semantics, not automatically covered by the two volumes above merely existing.
  - `docker logs` output and `/var/log/supervisor/` are **not durable across container recreation** unless separately, deliberately collected beforehand (§10, §18) — this is a directly-validated fact, not a theoretical caveat.
  Several production-hardening items remain open (first real member production deployment, full backup/restore rehearsal, image-upgrade rehearsal, HSM/PKCS#11 validation in this specific container context, container HA) — see the companion checklist.
- **CamDX 7.8.2 validation status:** **APPROVED / SAFE-EVIDENCED** for standalone deployment — build/provenance, runtime initialization, PKI, registration, live API exchange, restart/recreate/reboot persistence, and public GHCR publication are all validated (see [`../release-notes/7.8.2.md`](../release-notes/7.8.2.md)). This validation does **not** extend to container HA/Kubernetes (Model F) or to every production-hardening item in the companion checklist.
- **CamDX recommends this when:** the member is starting fresh and already operates other services on mature, hardened container infrastructure.
- **CamDX does not recommend this when:** it would be the member's first production container deployment of anything, when the member has a stable, working native Security Server with no operational pain point that containerization would solve, or when the member needs HA today (Model F is not yet CamDX-approved — see §7).

## 6. Model D — Independent Security Servers (simple redundancy)

- **Intended use:** members who want redundancy without adopting the replication/failover complexity of the clustered HA architecture (Model E) — two or more Security Servers, each with its **own, distinct Security Server Code**, independent credentials, independent local state, coexisting and each carrying live traffic, with traffic steering handled by the member (typically via their own load balancer or DNS).
- **Operational prerequisites:** each Security Server is deployed and registered independently (any combination of Models A/B/C); the member operates their own traffic-steering layer; CamDX Operational Monitoring observes each Security Server Code separately, not as a single logical pair.
- **Advantages:** no shared-state replication to design, secure, or operate (no PostgreSQL streaming replication, no `rsync`/`ssh` key-material propagation) — each server is a fully independent, self-contained unit. This significantly reduces the failure-mode surface area compared to Model E's replicated-state architecture.
- **Trade-offs:** each Security Server must be independently configured, patched, registered, and monitored — there is no single logical identity; consumers/providers may observe two distinct Security Server Codes rather than one. Provider-side behavior when a provider is expected to select among a member's multiple registered Security Server Codes via X-Road's own peer-selection/global-configuration mechanism is **not** yet resolved — see the explicit boundary below.
- **CamDX 7.8.2 validation status:** **Preferred simple redundancy model candidate. Targeted CamDX validation required.** This is **not** yet marked universally validated HA. The operator has existing **operational evidence** (not independently re-executed CamDX lab evidence) that independent Security Servers with different Security Server Codes can coexist, carry traffic, and be centrally monitored in real CamDX operation — this evidence supports the pattern's basic viability but does not constitute a completed CamDX validation program for it.
- **Provider-side boundary (do not overclaim):** whether direct X-Road provider-side peer-selection routing across a member's multiple Security Server Codes behaves as the member expects, in every provider/global-configuration scenario, is **targeted validation required if applicable** — not assumed resolved by the operator evidence above, which concerns member-controlled/load-balancer-mediated traffic, not provider-side routing decisions.
- **Relationship to the approved Parallel Replacement / Blue-Green migration pattern:** decision `03-A2` and [`upgrade/parallel-replacement.md`](./upgrade/parallel-replacement.md) use the same underlying mechanic (distinct Security Server Codes, independent state, coexistence) as a **temporary, transitional** technique for migrating one member from OLD to NEW. Model D is the same mechanic used as a **permanent, steady-state** redundancy architecture. The operator evidence behind 03-A2's approval is part of what supports Model D's basic viability, but approving 03-A2 as a migration pattern did not, by itself, validate Model D as a standing HA architecture — they are evaluated and gated separately.
- **Candidate for CamDX validation when:** a member wants redundancy with the least operational/security complexity and can operate their own traffic-steering layer, and does not require a single logical Security Server Code. **This is a preferred candidate, not yet an approved member deployment recommendation** — targeted CamDX validation (§6 above) is still required before it can be presented as a settled recommendation rather than a candidate.
- **CamDX does not recommend this when:** the member specifically requires a single logical Security Server Code/identity across the redundant pair (Model E), or requires validated provider-side automatic peer-selection failover without member-side traffic steering.

## 7. Model E — Replicated external-load-balancer HA cluster

- **Intended use:** members who need a single logical Security Server identity/configuration replicated across primary and secondary nodes, behind an external load balancer — CamDX's established, real-member HA architecture.
- **Operational prerequisites:** primary/secondary Security Server pair; a dedicated `serverconf` PostgreSQL instance with streaming replication between nodes; scheduled `rsync`+`ssh` propagation of the remaining shared `/etc/xroad` state; an external Layer-4/TLS-passthrough load balancer; `node.ini` role configuration on each node. Full detail: [`ubuntu/high-availability-installation.md`](./ubuntu/high-availability-installation.md), [`rhel/high-availability-installation.md`](./rhel/high-availability-installation.md).
- **Advantages:** a single logical Security Server Code/identity for consumers and providers; this is CamDX's most operationally mature HA pattern, in real use by existing members today; upstream X-Road's own external-load-balancer clustering guide documents essentially the same architecture, so it is **upstream-aligned**, not a CamDX-only invention.
- **Trade-offs:** materially more complex than Model D — requires PostgreSQL replication expertise, careful state-replication-scope discipline (see §5 of the Ubuntu HA document for exactly what is and is not replicated, and why), and accepts upstream's own stated limitation that this architecture prioritizes **load balancing**, not full fault tolerance — some in-flight messages can still be lost if a node fails, and failover/primary-promotion is a manual, not automatic, operation.
- **CamDX 7.8.2 validation status:** **Supported existing architecture. Upstream-aligned. CamDX 7.8.2 validation required.** This architecture **must be maintained and supported in documentation** — it is not being removed or deprecated because Models C, D, or F exist. It is **not** marked APPROVED for 7.8.2 until CamDX performs its own runtime validation of the specific items enumerated in the Ubuntu/RHEL HA documents.
- **Current posture, pending the CamDX 7.8.2 validation gate:** **existing members already running this architecture remain fully supported** — it is not deprecated, and CamDX continues documenting it as the correct architecture to preserve where a single logical Security Server identity is genuinely required. For a **new** 7.8.2 deployment, however, this model is **not presented as a generally recommended choice today** — it is not yet APPROVED for 7.8.2, and a new deployment should not be steered toward it ahead of the validation gate closing. **Once the CamDX 7.8.2 HA validation gate (§13 of the Ubuntu HA document) is complete, it may then be selected for a new deployment where the single-logical-identity requirement specifically justifies the additional replication/operational complexity** over Model D.
- **CamDX does not recommend this when:** the member would be satisfied with Model D's simpler independent-server redundancy and does not specifically need a single logical Security Server Code; or the member is starting a **new** 7.8.2 deployment and the validation gate above has not yet closed.

## 8. Model F — Container/Kubernetes HA

- **Intended use:** members who are both container-native (Model C) **and** want a cloud-native, orchestrated HA topology — a Primary/Secondary pod architecture with configuration synchronization, as documented by upstream's Kubernetes Security Server Sidecar guide.
- **Operational prerequisites:** a Kubernetes cluster (upstream's guide targets Amazon EKS/Azure AKS specifically); an **external PostgreSQL instance shared across pods** — this is the HA-capable database pattern upstream documents for the multi-pod topology; **per-pod local volumes are a separate, single-pod, non-HA option upstream describes for a different deployment shape and are not an equivalent database choice for this multi-pod topology** (do not present the two as interchangeable); Kubernetes Secrets for credential/key material; mature Kubernetes operational practice.
- **What Kubernetes actually changes vs. what it does not:** Kubernetes automates **pod lifecycle, readiness, scaling, and load-balancer membership** — real, upstream-documented advantages over manually operating VMs. **Kubernetes does not eliminate the primary-to-secondary configuration synchronization mechanism itself** — upstream's own multi-pod architecture still relies on the same kind of `rsync`/SSH-key-based synchronization described for the native VM cluster (implemented here as a per-minute cron job between pods, using SSH keys stored as Kubernetes Secrets), not a Kubernetes-native replacement for it. Do not describe Kubernetes as having removed the `rsync`/SSH/config-synchronization requirement — it relocates and reschedules it, it does not eliminate it.
- **Advantages:** horizontal scaling of secondary pods via standard Kubernetes primitives (readiness probes, Deployments, load-balancer service membership managed by Kubernetes itself rather than manual VM provisioning).
- **Trade-offs (do not overclaim — stated directly per upstream's own documentation):** upstream itself states that if the primary pod crashes, the synchronization cron job fails, though secondary pods can continue processing already-synced configuration; rolling upgrades are only possible when there are no database schema changes; this is explicitly a more complex topic that upstream itself scopes narrowly (e.g. Horizontal Pod Autoscaler support is called out as "out of scope" for upstream's own guide). Two containers on one Docker host, or a bare Docker Compose multi-container setup, is **not** the same thing as this Kubernetes HA architecture and must not be described as HA.
- **CamDX 7.8.2 validation status:** **Upstream-supported. CamDX validation required.** This is **not** presented as CamDX-approved HA, and it does **not** replace Model E — CamDX's existing native replicated-HA architecture remains supported for members who already use it.
- **Candidate for CamDX validation when:** a member is both container-native and Kubernetes-native, and specifically wants orchestrated HA rather than Model D's simpler independent-server pattern or Model E's native replicated-cluster pattern. **This is not yet an approved member deployment recommendation** — it is upstream-supported and CamDX-validation-required, nothing more, until that validation occurs.
- **CamDX does not recommend this when:** the member is not already Kubernetes-operations-mature, or is looking for the least-complex HA option (Model D) or CamDX's most evidenced HA option (Model E, pending its own validation).

## 9. What this document does not do

- It does not authorize moving an existing member from one model to another — see [`upgrade/README.md`](./upgrade/README.md) for why fresh-install/deployment-model documentation is never itself a migration authorization.
- It does not mark any HA model (D, E, or F) as CamDX-APPROVED — see each model's own status line above and the design-only validation plan in `CAMDX_HA_DEPLOYMENT_MODELS_REVIEW.md` (initiative workspace).
- It does not claim upstream support for a capability (e.g. PKCS#11/HSM, Kubernetes clustering) equals CamDX runtime validation of that capability in CamDX's specific deployment.
