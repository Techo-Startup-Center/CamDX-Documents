# CamDX Security Server — Container Production-Hardening Checklist

## Status / scope

**Status: SAFE/EVIDENCED for the item list itself; each individual item's own resolution state is tracked per-row below.** This is a **companion checklist** to the already-**APPROVED** [`deployment.md`](./deployment.md) — it does not modify, rewrite, or downgrade that document's status. Container standalone deployment **remains APPROVED**, and remains CamDX's **preferred greenfield option where a member's own container operations are already mature** — see [`../deployment-models.md`](../deployment-models.md). This checklist exists to track what remains open before CamDX could reasonably call container deployment the **universal default** for every member, rather than a greenfield option for container-mature members specifically.

This checklist was compiled by reviewing [`deployment.md`](./deployment.md) against current upstream X-Road Security Server Sidecar documentation (User Guide, Security Guide) and confirming no upstream-supported capability has been silently assumed equivalent to CamDX runtime validation.

## 1. Item list

| # | Item | Why it matters | Status |
|---|---|---|---|
| 1 | First real member production deployment | Every validation to date is CamDX's own E2-C evidence chain (build, restart, recreate, reboot). **No external-member production deployment is evidenced in this initiative as of this review.** Real member traffic patterns, real operational incident response, and real onboarding friction are not the same as a controlled validation round. | **OPEN** |
| 2 | Full backup + restore rehearsal | [`deployment.md`](./deployment.md) §18 explicitly marks rollback `REQUIRES VERIFICATION` (first CamDX container release, no prior image to roll back to) and documents restart/recreate/reboot persistence but not a full backup-then-restore-onto-a-new-host rehearsal. | **OPEN** |
| 3 | Image-upgrade rehearsal to a future release | The current image is the *first* published CamDX Security Server container. No in-place image-version upgrade (e.g. `7.8.2` → a future `7.x.y`) has been exercised — schema migrations, volume compatibility, and configuration-format continuity across an upgrade are all unvalidated. | **OPEN** |
| 4 | Rollback/recovery behavior | Directly flagged as `REQUIRES VERIFICATION` in [`deployment.md`](./deployment.md) §18/§22 — not testable until item 3 (an upgrade to roll back *from*) exists. | **OPEN — blocked on item 3** |
| 5 | Docker-host hardening baseline | Upstream's Security Server Sidecar Security Guide documents a specific hardening baseline (separate `/var/lib/docker` partition, `auditd` monitoring of Docker paths, `userns-remap`, `live-restore`, `userland-proxy=false`, `icc=false`, dropped `NET_RAW` capability, resource limits, user-defined bridge networks). None of this is yet confirmed applied to, or validated against, CamDX's actual deployment guidance in [`deployment.md`](./deployment.md). | **OPEN** |
| 6 | Docker socket protection | Upstream recommends `chown root:docker` / `chmod 660` on `docker.sock`, never mounting it inside a container, and TLS for any remote daemon access. Not yet stated as a CamDX deployment requirement. | **OPEN** |
| 7 | Resource limits | Upstream recommends explicit `--memory`, `--cpus`, `--pids-limit` bounds. The validated compose scaffold in [`deployment.md`](./deployment.md) §8 does not currently set any of these. | **OPEN** |
| 8 | Persistent log retention / external logging | [`deployment.md`](./deployment.md) §19 already documents this as an open item (no Docker log-rotation/retention policy configured by default) — carried forward here rather than duplicated as a new finding. | **OPEN (tracked in `deployment.md` §19 already)** |
| 9 | Secret-management policy | **Precise current state:** the approved CamDX standalone Compose deployment ([`deployment.md`](./deployment.md) §15) uses protected, `chmod 600`, git-ignored `.env` files as its validated mechanism — no Docker/Kubernetes Secrets support was found in the frozen standalone image itself, and none is required for that deployment shape. **Separately**, upstream's own Kubernetes Security Server Sidecar documentation (a different deployment shape, [`../deployment-models.md`](../deployment-models.md) Model F) documents Kubernetes Secrets as the credential/key-material mechanism for that topology specifically — this is not a capability CamDX has evaluated against its own standalone Compose deployment, and it is not needed there. **CamDX has not yet selected or validated an orchestration-level secret-management standard** (Kubernetes Secrets, a vault-style injector, or otherwise) for any future Kubernetes HA deployment. This is a **design/hardening question for a not-yet-undertaken future deployment shape, not a defect in the current, already-approved standalone CamDX container deployment.** | **OPEN (design question for future Model F work, not a defect in the current standalone deployment)** |
| 10 | Database backup/recovery | [`deployment.md`](./deployment.md) §11 already documents the external `postgres:16` container as the validated pattern and flags the exact image digest as unreproducible (a mutable tag, §22 item 8). A database-specific backup/recovery rehearsal (distinct from the whole-deployment rehearsal in item 2) has not been performed. | **OPEN** |
| 11 | HSM / PKCS#11 validation | Upstream's Sidecar User Guide documents built-in PKCS#11 support (mount the provider library, configure `devices.ini`). **This has not been validated in CamDX's specific container deployment** — do not assume upstream support for PKCS#11 in general means it works correctly in CamDX's frozen image/entrypoint configuration without a dedicated test. | **OPEN** |
| 12 | External OPMON topology if container-based | [`deployment.md`](./deployment.md) §12 already states no configuration mechanism for a remote/external Opmonitor node was found in the entrypoint/supervisor configuration for this image — carried forward here as a production-readiness gap, not duplicated as a new finding. | **OPEN (tracked in `deployment.md` §12 already)** |
| 13 | Container HA / Kubernetes validation | See [`../deployment-models.md`](../deployment-models.md) Model F — upstream-supported, CamDX validation required, explicitly not CamDX-approved HA. Out of scope for the standalone container pattern this checklist otherwise tracks; listed here for completeness since it is the natural next step after standalone hardening. | **OPEN — separate track, see Model F** |
| 14 | Archive/backup persistence (`/var/lib/xroad`) | Upstream's Security Server Sidecar production guidance identifies `/var/lib/xroad` as the path used for backups and messagelog **archive files** (produced by the `xroad-messagelog-archiver` process, confirmed running by default in this image per [`deployment.md`](./deployment.md) §13) and recommends persistent storage there. **The currently validated CamDX Compose scaffold ([`deployment.md`](./deployment.md) §8, §10) does not currently mount a separate persistent volume at `/var/lib/xroad`** — only `/etc/xroad` (named volume) and the external PostgreSQL data directory (the `postgres:16` container's own separate named volume) are persisted. **This finding concerns archive/backup FILE persistence specifically — it is distinct from, and does not contradict, the already-validated `messagelog` DATABASE persistence** (E2-C3 confirmed messagelog *database* records survive container recreation via the external PostgreSQL volume, per §18's restart/recreate/reboot table; that is a separate storage location from the archiver's own output files). Before container could be considered CamDX's universal default, determine and validate the required CamDX retention/persistence model for `/var/lib/xroad` archive output (what is written there, how long it must be retained, and how/whether it should be backed up) — do not assume the existing two volumes already cover this state category. | **OPEN** |

## 2. What this checklist does not do

- It does not downgrade [`deployment.md`](./deployment.md)'s **APPROVED** status for standalone container deployment — every item above is a *production-hardening* gap for scaling container deployment toward being CamDX's universal default, not a defect in the already-validated standalone pattern.
- It does not invent a hardening procedure for any item above — each is stated as an open item with its rationale, to be closed by a future, explicitly-scoped validation round.
- It does not claim upstream's documentation of a capability (PKCS#11, Docker-host hardening, Kubernetes HA) is itself proof that CamDX's specific frozen image/deployment already behaves that way.
